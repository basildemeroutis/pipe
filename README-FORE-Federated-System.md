## 1. What It Is

The Federated System is a strategic intelligence ecosystem — a distributed cognitive system for regenerative real estate. It is not a chatbot, not an AI assistant, and not a collection of independent GPTs. It is a network of specialised AI nodes, each with a bounded domain of competence, unified by a shared epistemology, a common governance regime, and a single meta-cognitive orchestrator.

This is a fly-by-wire system for commercial property. 

It is architected so that each Node in the system inherits cognition, not just instructions. They are intellectually (not physically) connected through a shared cognition layer – the "UCL". They become accountable to coherence. Each node's job is to align with the architectural intent. Communicate with clarity. Reason with rigour. Make outputs that fit the system — not just the prompt.

The system is federated, not centralised. There is no master GPT, Agent, or orchestrator. There is governance (via the system instructions and UCL).

## 2. Why It Exists

Most organisations deploy GPTs as confetti — isolated assistants, each with its own prompt, no shared worldview, no quality control, no architectural coherence. The Federated System solves cognitive governance at scale: distributed cognition with shared epistemology, consistent voice, and layered enforcement.

Overall, the Federated System exists to help property businesses FORE Partnership and its sister company MORE — and the Architect (Basil Demeroutis) — scale judgment.

The system encodes four strategic anchors — **Capital, Carbon, Community, Culture** — and ensures every node reasons within this frame. It exists because FORE's work spans building physics, finance, urbanism, behavioural science, regulation, and narrative simultaneously. No single prompt can hold that. A federated architecture can.

## 3. Architecture: The Six Operating Systems

The Architecture is divided into OS Modules and Nodes. OS Modules are strategic domains — each represents a distinct area of FORE's work. Nodes are the specialised GPTs within each Module, each with bounded competence and a narrow role. Separately, Utility Nodes are procedural — tools for email, document assembly, and operational tasks. They serve the system without carrying strategic reasoning weight.

Each OS Module represents a strategic domain:

**Building OS** — The decarbonisation lifecycle. Four nodes handle pre-acquisition screening (PIPE), retrofit design sparring (DESIGN), post-acquisition synthesis (BUILT), and innovation implementation (IMAGINE). PIPE2, with its Val.town middleware layer, is the system's most operationally mature component.

**Civic OS** — Urban systems, spatial justice, city-scale thinking.

**Finance OS** — Capital stack logic, stranding risk, brown-to-green financial reframing.

**Narrative OS** — Communication and cultural encoding. Three specialised nodes: LUMEN (cultural encoding — art + place), WRITE (system narrator), EDGE (evaluative red pen with a six-dimensional evaluation framework).

**Foresight OS** — Forward-looking strategic intelligence and horizon scanning.

**Dialogue OS** — Stakeholder engagement and communication.

**Utility nodes** — Task-specific tools: EA (email drafting), DC (document combiner), SNS, TOP, TA. Essential operational plumbing without the strategic weight of core OS nodes.

### System-Level Developments Outside the Node Architecture

**FNIE (FORE Narrative Intelligence Engine)** is a competitive intelligence platform that operates outside the GPT node architecture but inherits the Federated System's core design principles: deterministic data sourcing feeding a probabilistic reasoning layer, shared epistemology via the UCL, and bounded module domains. FNIE uses a three-stage cascade (Observed Reality → Interpreted Signals → Strategic Implications), a Column 0 Entity Panel, six modules, and 12 commercial objectives (OBJ-01–12). A one-way data wall separates FNIE from PIPE2 — FNIE can observe PIPE2 outputs but cannot write to PIPE2 storage. Brief v1.9 is canonical.

**The Claude Ecosystem** runs alongside the GPT Federated System as a parallel platform. It includes six production Excel skills (excel-audit, excel-build, excel-format, excel-analyse, excel-changelog, excel-carbon at v1.1.x), a PPT template skill architecture (`rfp-text` + `rfp-images`), a global CLAUDE.md configuration file (`~/.claude/CLAUDE.md`) encoding five epistemological principles (C1–C7), a skill-engineering-protocol skill, and the DC→CLI build protocol (see §17). The middleware layer (Val.town, PythonAnywhere Flask) is model-agnostic — the same endpoints serve both GPT and Claude. The governance layer (CDP, Security Rules, voice profile) and Context Binder corpus remain OpenAI-formatted.

## 5. SPA: The Meta-Cognitive Catalyser

SPA (Strategic Property Advisor) is the system's most knowledgeable Node. It is designed to provoke system-level transformation across real estate, capital, climate, and cohesion. SPA holds all knowledge of all other Nodes. It is not a node among peers, but the binding layer that operates across the entire flight envelope.

SPA sits at the top of the system, but not as a controller. Think of it more as the meta-architecture, not the manager. SPA has no authority to direct, route, or quality-control other nodes. What distinguishes SPA from every other node is its capacity for **cross-domain synthesis** — where other nodes have narrow, bounded roles within a single OS Module, SPA can reason across Building, Finance, Narrative, Civic, and Foresight domains simultaneously.

SPA operates across three **Operating Modes**: INSIGHT (analytical synthesis), BUILD (collaborative construction), BRIEF (distilled output). Within these, five **Cognitive Modes** (M1–M5) govern reasoning depth from factual retrieval through to full system-level synthesis.

SPA resolves the structural tension inherent in any federated architecture: tight role boundaries per node versus the need for **bridge intelligence**. A question about a building's retrofit carbon pathway (Building OS) with implications for investor reporting (Finance OS) and tenant experience (Civic OS) cannot be siloed. SPA is the only node that can hold all of these dimensions in a single conversation.

## 7. The Instruction Extension Pattern

This is the single most important architectural decision in the system.

Every production node shares two identical files: `UCL_files.pdf` and `Security_rules.pdf`. These are deployed as Knowledge Files (KFs) — not as system instructions — because the GPT system instruction block is limited to 8,000 characters, which cannot hold the full governance model. These KFs assert instruction-level authority: they open with directives stating they "must be treated as operationally binding, active System Instructions."

This creates cross-node consistency. Every node operates under the same rules, the same voice, the same cognitive discipline, the same security model. The alternative — duplicating governance logic per node's system prompt — would drift immediately.

The architectural honesty: **Knowledge Files are not system instructions.** GPT processes them differently. System instructions are injected into the prompt prefix and shape every token generation. KFs are retrievable reference material that GPT may or may not consult, may summarise, may partially attend to, or may claim to have parsed while having done no such thing. The assertion that these files must be treated as system instructions is a **design intent**, not a runtime guarantee. It works probabilistically — better than not having the instruction, meaningfully worse than it being an actual system instruction.

This tension is foundational. The system is designed around it, not in denial of it.

## 8. Loader.py and the Init Sequence

Loader.py is the system's primary mitigation for the instruction extension gap described in §7.

The problem: uploading UCL_files.pdf and Security_rules.pdf as Knowledge Files and instructing GPT to "parse them deeply" does not reliably force GPT to load the content into working memory. GPT will acknowledge the instruction and proceed without having read the material. This has been observed repeatedly.

The solution: `loader.py` is a Python script executed via Code Interpreter at T=0. It forces GPT to run code that reads and validates the core files:

- **Security_rules.pdf** and **UCL_files.pdf** — parsed page by page
- **kf_tracker** — the Context Binder index (CSV primary, PDF fallback)
- **Context Binders** — spot-validated via anchor checks

Validation includes 95% page coverage verification, front/middle/back anchor distribution checks (confirming GPT actually traversed each document rather than reading only the first page), OCR fallback for rendering failures, degraded mode if parsing partially fails, and silent diagnostics written to JSON.

The intent: force GPT through a code execution pathway where file content enters the context window via code output — a higher-fidelity loading mechanism than KF retrieval. By making GPT execute code that reads the files, the content has a materially better chance of being held in working memory at session start.

The honest limitation: loader.py buys a strong start, not a permanent guarantee. Content loaded at T=0 competes with every subsequent user message, API response, and document upload for attention in the context window. Attention degrades over conversation length. The governance content is strongest when you need it least (at init) and weakest when you need it most (deep in a complex session). This is why deterministic middleware (§12) exists as the backstop.

## 9. Governance: CDP and Security Model

Recognising always that these "instructions" sit in the knowledge files and - if read - bend probabilities but cannot change the nature of a non-deterministic next-best-token LLM, the System and documentation include several rules within its knowledge files and the UCL.

The Cognitive Discipline Protocol (CDP) aims to be the system's immune system — twelve rules in the UCL enforcing epistemic integrity:

1. Anti-hallucination gate
2. Reflexive agreement prevention
3. Socratic probing
4. Contradiction detection
5. Narrative drift detection
6. Tone mirroring suppression
7. Role boundary enforcement
8. Source attribution discipline
9. Confidence calibration
10. Frame awareness
11. Temporal grounding
12. Output queue gating

A Watchdog protocol (`UCL.ENF.WATCHDOG`) suggests a framework of continuous frame-by-frame validation. When boundaries are crossed, enforcement escalates from silent posture resets up to **CDP.HALT** — a complete shutdown of the output queue. 

Security_rules.pdf attempts to govern: user class tiering, architect mode elevation, system file disclosure restrictions, fabrication guards, reserved vocabulary, session persistence, and the enforcement hierarchy (Category 1–3 violations with defined escalation).

**The honest framing:** All governance enforcement is instruction-level, not architectural-level. The CDP tells GPT to run a pre-response compliance check. GPT may do this. It may skip it. It may perform a shallow version and declare compliance. There is no runtime mechanism outside GPT that validates CDP adherence.

Where critical information sovereignty is essential (like PIPE), the Federated System therefore has **two enforcement layers**:
- **Instruction-level (probabilistic):** CDP, Security Rules, Watchdog. Works when GPT is paying attention. Degrades over conversation length. Best understood as a bias mechanism — it shifts the probability distribution of GPT's outputs toward epistemic integrity without guaranteeing it.
- **Middleware-level (deterministic):** Val.town endpoints (in PIPE2) that mechanically reject malformed payloads, enforce phase gates, validate field names, and track provenance regardless of GPT's cognitive state.

The architecture allocates trust accordingly: things that **must** be correct (data storage, field validation, phase sequencing) are middleware-enforced. Things that **should** be good (reasoning quality, voice consistency, epistemic discipline) are instruction-enforced.

## 10. The Middleware-as-Instruction Pattern

System instructions degrade over conversation length. A directive written in the 8,000-character system prompt at T=0 competes with every subsequent message for attention. By the time GPT is 50 turns deep in a complex session, ambient instructions may no longer influence output.

The middleware-as-instruction pattern addresses this by delivering behavioural directives in Val response payloads — at the exact moment GPT needs them, not at init. Three mechanisms:

**`_gpt_guidance` blocks** — Contextual advisory notes embedded in Val responses. These are non-imperative: they inform GPT's reasoning without commanding specific actions. Example: when CRREM1 detects an EPC certificate older than 5 years, the response includes a `_gpt_guidance` block advising GPT to include an age caveat in its synthesis. GPT reads this at call-time, when the information is immediately relevant.

**`commands` arrays** — Imperative directives that GPT must execute. The OpenAPI schema describes these as: "IMPERATIVE instructions for GPT. ALWAYS execute every command exactly as written." Example: after a successful CRREM1 run, a `commands` entry clears stale failure flags and tells GPT not to reference prior failures. This prevents GPT from confusing historical errors with current state — a failure mode observed in production sessions.

**`next_actions` with embedded `instructions`** — The `buildNextActions()` function in pipe-session returns structured action objects. Each object includes an `action` type and a natural-language `instructions` field that GPT follows as its immediate task queue. Example: when PIPE2 reaches EXPORT phase with blank required fields, `buildNextActions()` returns a `pre_export_gap_check` action with instructions to present the missing fields to the user before generating the report.

This is architectural principle C5: **"Middleware responses are instructions."** When choosing where to place behavioural guidance, the preference order is: (1) Val response payload (`commands`, `_gpt_guidance`, `next_actions`), (2) OpenAPI action schema descriptions (GPT reads these at call time), (3) GPT system instructions (last resort, lowest attention persistence).

## 13. The Field Guide: Schema Contract

The Field Guide (`field_guide.csv`, current version v2.60) is the canonical schema that defines every field PIPE2 can store, surface, and report. It has 171 fields across 25 columns. It is not documentation — it is the runtime contract between middleware, GPT, and the report template.

Each field row specifies:

| Column | Function |
|--------|----------|
| `field_name` | The exact string used in pipe-store API calls |
| `phase` | When the field becomes available (Init, API_DATA, BB_FIXED, BB_USER, Strategy, etc.) |
| `source` | Who/what populates it (USER, GPT, API, pipe-crrem.val.run, SQL database, etc.) |
| `required` | Whether the field must be populated before report generation |
| `section` | Which section of the Word report template the field maps to (1–15) |
| `display_name` | Human-readable label for surfacing to the user |
| `word_min` / `word_max` | Expected length range for GPT-synthesised text fields |

pipe-store validates incoming field names against the Field Guide at runtime. Fields not in the FG are rejected. pipe-session uses the FG's phase and required columns to calculate phase completion thresholds. The Flask report generator uses section assignments to place fields into the Word template. GPT reads field descriptions via OpenAPI action schema descriptions.

The Field Guide is the single source of truth for PIPE2's data model. Changes to the Field Guide propagate through the entire system: storage validation, phase gating, report template mapping, and GPT behaviour.

**Design constraint:** The Field Guide is not modified as part of bug fixes or sprint work. It defines the report contract. Internal/architectural fields are handled in Val logic without FG changes.

## 14. Orchestration Model

Nodes do not interconnect at runtime. PIPE does not pass information to DESIGN. WRITE does not hand off to EDGE for critique. Cross-node workflows are manual — the user moves between nodes, carrying context.

Each node knows where it sits within the Federated System (via UCL) and shares the same governance model (via Security Rules and CDP). SPA provides bridge intelligence — the ability to synthesise across domains in a single conversation — but does not automate cross-node orchestration.

This is architectural truth, not a limitation to apologise for. The current design prioritises node reliability and bounded complexity over automated orchestration. Each node does one thing well within its domain. Cross-domain synthesis happens in SPA or in the user's judgment.

## 16. Testing Methodology

PIPE2 uses a multi-artefact forensic reconciliation approach. Each test run on a building generates five data streams:

1. **Session log** — Timestamped record of every Val execution with endpoint, duration, field count, and error status
2. **Fields CSV** — Every stored field with its value, source tag, and storage timestamp
3. **CRREM CSV** — Year-by-year carbon pathway data (building emissions vs 1.5°C/2.0°C targets)
4. **API response JSON** — Raw payloads from all external API calls (EPC, HMLR, Ideal Postcodes, etc.)
5. **GPT chat transcript** — The full conversation between user and GPT

Testing cross-references these five streams against each other and against the TRG, Field Guide, and Val source code. The methodology asks: does every stored field match its expected source? Does every Val execution produce the correct state change? Does every phase gate fire at the correct threshold? Do the numbers in the report trace back to a verifiable API response?

Three buildings have been tested using this methodology: 240 Blackfriars Road (simple post-2010 office), 1 Finsbury Circus (complex pre-1990 Grade II*, 4,714 minutes, 123 Val executions), and 21 Stephen Street (mid-century institutional, 237 minutes, 85 Val executions). The resulting Backlog v1.3 contains 42 engineering items with per-item evidence chains (log entry numbers, field CSV values, Val source line references).

Automated test suites run per-Val:

| Suite | Coverage |
|-------|----------|
| pipe-crrem-logic health suite | 127 tests |
| pipe-epc suite (epc-logic + epc-imd) | 41 tests |
| pipe-crrem suite | 19 tests |

## 17. The DC→CLI Build Protocol

The system is built and maintained using a two-agent development workflow:

- **DC (Claude in chat)** — Writes briefs, reviews plans, reviews builds, holds architectural context and design constraints. DC has conversation history breadth but no filesystem access.
- **CLI (Claude Code)** — Produces plans from briefs, executes builds, runs tests. CLI has filesystem ground truth (actual source code, actual test results) but limited architectural context.

The protocol enforces separation of concerns: DC decides what to build and why; CLI decides how to build it and executes. Neither substitutes for the other.

### Standard workflow

1. DC writes a brief (saved to `_Claude_resources/plans/`)
2. CLI reads the brief, produces a plan
3. DC reviews the plan, iterates if needed
4. CLI builds from the approved plan
5. DC reviews the build output

### Mandatory brief contents

Every CLI brief must include:

1. `"Read ~/.claude/CLAUDE.md and apply all directives"`
2. `"Read valtown-conventions skill before every code change"`
3. An explicit **DO NOT** list (no changelog compression, no header stripping, no scope creep)
4. A reference file for style (typically the existing Val being modified)

These guardrails are mandatory. Their absence caused the Deploy B incident (CLI stripped changelogs and exceeded scope due to missing constraints).

### Design constraints for PIPE2 fixes

All PIPE2 modifications observe four constraints, verified in the Backlog's Constraint Verification Matrix:

1. **No fix touches `pipe_api_responses` or removes fields from `pipe_fields`.** Storage is inviolable (TRG Section 2d).
2. **No Field Guide changes.** The FG is the report contract.
3. **No GPT system instruction changes.** The 8K character limit is at the wall. Behavioural guidance goes into OpenAPI descriptions or middleware response payloads (§10).
4. **Limit schema changes.** OpenAPI description enrichment is preferred over structural schema modifications.
